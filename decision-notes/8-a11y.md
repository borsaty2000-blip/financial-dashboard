# Accessibility

In the first version I was not ignoring semantics, but I also did not treat accessibility as a separate part of the component architecture.

My approach was closer to: use normal HTML and do not do anything obviously broken.

Once I tested the table and chart through actual keyboard focus, expansion, and horizontal scrolling behavior, I started checking more than which tags existed in JSX. I wanted to know what actually happens with the keyboard, where focus goes, and whether my own implementation accidentally breaks native browser behavior.

Expandable table rows are a good example.

The easiest implementation is to put `onClick` on the whole `<tr>`.

But a `<tr>` is not a button.

Then I would need `tabIndex`, a role, manual Enter handling, manual Space handling, and I would basically be rebuilding native button behavior myself.

I decided to do it differently.

Interaction only exists where there is actually an action.

The row-header cell of an expandable row contains a normal button with `aria-expanded`.

A leaf row is not interactive at all.

The browser already provides the keyboard semantics for the button instead of me imitating them.

The table also remains a real table: `table`, `caption`, `th scope="col"`, and `th scope="row"`.

The horizontally scrollable container can receive keyboard focus and has an accessible name through the caption.

The sticky first column stays a normal part of the table and does not put a separate interactive layer over the row, so touch scrolling does not need to be broken just to implement the design.

The chart is slightly more complicated because part of the behavior comes from Recharts.

I use their `accessibilityLayer`, provide a title and description for the focusable SVG, and keep a visible focus state.

That last part was a good example of why I no longer wanted to judge accessibility only by looking at JSX. You can add the right focus style and then kill it with one `outline-none` utility later.

So the final behavior matters, not only whether an ARIA attribute exists somewhere in the source.

I also deliberately kept the visual palette from the current design. I could change colors or add stronger separators between stacked segments, but that starts conflicting with the goal of preserving the design.

The values are not communicated by color alone anyway: there is a legend, a tooltip, and the full table. For this project I chose to preserve the current visual design.
