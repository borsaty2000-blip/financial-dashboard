# تقييم الملف `pasted_content_19.txt`

**التاريخ:** 17 سبتمبر 2026

## 1. الحكم التنفيذي

الملف جيد كخارطة طريق، لكنه ليس صالحاً للتنفيذ كما هو دون ضبط ثلاثة أمور: **ترخيص مصدر البيانات، تعريف معنى السعر اللحظي، وفصل التحليل الاحتمالي عن التوصية الاستثمارية**. أهم استنتاج صحيح فيه هو أن Yahoo Finance لا يكفي لبناء Tick-by-Tick أو Order Flow للأسهم المصرية والسعودية. أما اعتبار Twelve Data أو SAHMK ضماناً تلقائياً للبيانات الحية، فذلك يتوقف على الخطة والعقد وتغطية الرمز والفاصل الزمني، ولا يجوز إثباته من وجود مفتاح API فقط.

## 2. ما يتوافق مع الواقع الحالي

| بند الملف | الحالة الفعلية |
|---|---|
| Polling تكيفي 5 ثوانٍ للحي و30 ثانية للمتأخر | منفذ في `useLivePrice` |
| منع تداخل الطلبات | منفذ عبر حارس الطلبات النشط |
| فصل السعر الحي عن التاريخي | منفذ في رأس صفحة السهم |
| إعلان `freshness` و`source` | موجود في عقد السعر |
| Yahoo كـ fallback متأخر | موجود ومختبر |
| تحليل Elliott/Gann المتقدم | توجد محركات Pro وMTF وجسور Node/Python |
| تقرير advanced analysis | endpoint الإنتاج يعيد HTTP 200 |
| اختبارات الخادم | 28 اختباراً ناجحاً في آخر تحقق |
| البناء | ناجح في آخر تحقق |

## 3. أهم نتيجة إنتاجية يجب عدم تجاهلها

الاختبار الفعلي على الإنتاج أعاد:

- `COMI`: المصدر `Yahoo Finance`، والحالة `delayed`.
- `1010`: المصدر `Yahoo Finance`، والحالة `delayed`.
- `/api/health`: HTTP 200.
- `/api/analysis/1010/advanced?market=TASI`: HTTP 200، مع إعلان الحقول غير المتاحة مثل `realtime_tick`.

إذن المنصة تعمل، لكنها **لم تثبت بعد وجود بث لحظي مرخّص لأسهم EGX وTASI**. يجب ألا تظهر للمستخدم عبارة "لحظي" إلا عندما يعيد المزود حالة حيّة موثقة ويكون عمر الطابع الزمني ضمن حد مقبول.

## 4. تصحيحات ضرورية على Master Prompt v2

### أ. أولوية المزودين

الملف يقترح أولوية Twelve Data ثم SAHMK، بينما التنفيذ الحالي يستخدم SAHMK أولاً للسوق السعودي ثم Twelve Data ثم المصادر الاحتياطية. يجب أن تكون الأولوية قابلة للتهيئة، لا ثابتة داخل الكود، لأن الأفضلية تتغير حسب:

- تغطية الرمز.
- صلاحية الخطة.
- زمن الاستجابة.
- حالة السوق.
- حدود الطلبات.
- هل السعر Trade حقيقي أم EOD/Delayed.

### ب. Twelve Data لا يعني تلقائياً Real-Time

وجود `TWELVE_DATA_API_KEY` لا يكفي. يجب التحقق من:

1. استجابة المزود نفسها.
2. `datetime` أو timestamp.
3. عمر البيانات مقارنة بوقت الخادم.
4. صلاحية الفاصل `1m` أو Tick حسب الخطة.
5. تغطية EGX وTASI للرمز المطلوب.
6. شروط الترخيص وإعادة العرض للمستخدمين.

### ج. SAHMK لا يجب اعتباره حلاً تلقائياً لكل مصر والسعودية

يجب اختبار الرمز والسوق والحقول الراجعة فعلياً. إذا كانت الاستجابة لا تتضمن timestamp حديثاً أو تعلن `is_delayed`، فالتصنيف يجب أن يبقى delayed حتى لو كان endpoint اسمه quote.

### د. Binance خارج نطاق أسهم EGX/TASI

Binance مناسب للعملات الرقمية فقط. لا يجوز استخدام نجاح WebSocket الخاص به كدليل على لحظية الأسهم المصرية أو السعودية.

## 5. تقييم طبقات التحليل المقترحة

### Elliott Wave

المحرك الحالي يمكنه إنتاج عدّ موجي وأهداف وإبطال، لكن Elliott Wave ليس قياساً حتمياً. يجب أن تعرض الواجهة:

- درجة اكتمال البيانات.
- العد الأساسي والبديل.
- مستوى الإبطال.
- سبب اختيار العد.
- الثقة كـ **ثقة في توافق الأدلة**، وليس احتمال ربح.

لا ينبغي استخدام عبارة "تنبؤ صحيح" أو ضمان نجاح الهدف.

### Gann

الزوايا والدورات مفيدة كإطار تحليلي، لكنها لا تعطي تاريخ انعكاس يقينياً. يجب عرض الدورات كنوافذ محتملة مع هامش وعدم يقين، كما يذكر الملف نفسه.

### Harmonic وClassical Patterns

هذه الطبقات لا ينبغي أن تعيد اسم نموذج إلا بعد تحقق نقاط X-A-B-C-D أو شروط النموذج. عند عدم كفاية pivots يجب إرجاع:

```json
{
  "status": "insufficient_data",
  "pattern": null,
  "missing": ["confirmed_pivots"]
}
```

وليس نموذجاً فارغاً أو مكتشفاً اعتماداً على تشابه شكلي ضعيف.

### Confluence Score

الأوزان المذكورة تجمع إلى 105% عند جمع العناصر الواردة في الملف؛ لذلك لا يمكن تطبيقها كما هي. يجب إعادة التطبيع إلى 100% أو تحديد أن أحد العناصر مشروط. كذلك يجب فصل:

- `bullish_confluence`: درجة توافق الأدلة الصاعدة.
- `bearish_confluence`: درجة توافق الأدلة الهابطة.
- `missing_data`: ما لم يدخل في الحساب.
- `confidence`: جودة البيانات واتساقها، وليس احتمال نجاح الصفقة.

### Recommendation

الصيغة المقترحة مناسبة كـ decision-support، لكن كلمة `BUY` وحدها خطرة. الأفضل عرض:

> إعداد صاعد محتمل بشرط تحقق كذا، ويُبطل تحت كذا.

ويجب أن تتضمن التوصية نوع السوق، الفاصل، timestamp، مصدر البيانات، وقيود السيولة والسبريد.

## 6. PDF

الفكرة مناسبة، لكن تنفيذ PDF العربي يحتاج قبل اعتماده:

- خط عربي مرخص ومضمّن.
- RTL واختبار اتصال الحروف العربية.
- تضمين timestamp ومصدر كل رسم.
- عدم وضع أرقام أو أهداف غير موجودة في البيانات.
- تمييز التقرير المتأخر عن الحي في الغلاف.
- عدم إنشاء PDF يبدو رسمياً أو كأنه توصية مرخصة دون إخلاء واضح.

مسار PDF الحالي في الواجهة موجود كرابط، لكن يجب اختبار أن endpoint التقرير نفسه موجود ويعيد `application/pdf` فعلياً قبل إعلان هذه المرحلة مكتملة.

## 7. Backtesting

المتطلبات صحيحة من ناحية الاتجاه، لكنها تحتاج قيوداً إضافية قبل اعتماد النتائج:

- فصل In-sample وOut-of-sample فعلياً.
- عدم استعمال بيانات مستقبلية لحساب المؤشر في لحظة الإشارة.
- احتساب العمولة والانزلاق السعري وحدود السيولة.
- عدم استعمال قائمة الأسهم الحالية كبديل عن تاريخ الشركات، لتجنب survivorship bias.
- توثيق عدد الأيام والفواصل التي فشل فيها المصدر.
- رفض النتيجة أو وضعها `insufficient_data` عند قلة التاريخ.

## 8. معيار القبول المقترح قبل النشر

لا يُعلن الإصدار مكتملاً إلا إذا تحققت كل النقاط التالية:

1. `COMI`, `ABUK`, `1010`, `BTCUSDT`, و`XAUUSD` تُختبر كلٌّ في سوقه الصحيح.
2. كل response يعيد `provider`, `freshness`, `timestamp`, و`warnings`.
3. لا يظهر `live` إذا كان عمر البيانات خارج الحد المحدد.
4. عند غياب مزود حي، يظهر `delayed` مع سبب واضح.
5. ARIMA وLSTM وEnsemble ليست قيماً متطابقة إلا إذا كان التطابق مفسراً ومثبتاً.
6. Elliott وGann يعيدان أهدافاً فقط عندما يكون لها أساس سعري موثق.
7. كل إطار زمني غير متوفر يظهر كـ `unavailable`، لا كرقم وهمي.
8. التقرير المتقدم يذكر الأدلة المؤيدة والمعارضة والبيانات الناقصة.
9. PDF يختبر من ناحية RTL والخط ووجود الرسم والبيانات.
10. الاختبارات تشمل endpoint وواجهة العرض، وليس unit tests فقط.

## 9. القرار الهندسي

المرحلة الصحيحة التالية ليست إضافة عشرات المؤشرات دفعة واحدة. الأولوية هي:

1. **إكمال Provider Abstraction وProvider Router مع فحص freshness حقيقي.**
2. **تفعيل مزود مدفوع أو مرخص فعلياً ثم إثباته على EGX وTASI برمز محدد.**
3. **توحيد عقد `data_quality` في السعر والشموع والتحليل وPDF.**
4. **اختبار التحليل المتقدم على الرموز الخمسة مع حالات نقص البيانات.**
5. بعد ذلك فقط: Harmonic، PDF، ثم Backtesting الموسع.

## الخلاصة

الملف يحدد الاتجاه الصحيح، لكنه يبالغ في ربط مفتاح API بالدقة اللحظية وفي اعتبار الطبقات التحليلية قابلة لإنتاج تنبؤات صحيحة. الإصدار الحالي قوي من ناحية **الشفافية والبنية الاحتياطية**، لكنه يحتاج إثبات مزود حي مرخص قبل وصف الأسعار بأنها لحظية، ويحتاج إبقاء نتائج Elliott/Gann/Confluence في إطار **دعم القرار الاحتمالي** لا التنبؤ المضمون.

**التوصية:** اعتماد الملف كخطة تنفيذ مشروطة، وليس كإقرار بأن كل المراحل منفذة أو أن كل الأسعار لحظية بالفعل.
